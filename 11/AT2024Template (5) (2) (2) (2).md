# 1\. Введение

Настоящий документ — спецификация требований к программному обеспечению (SRS) системы аналитики и трекинга футбольных матчей, составленная с опорой на \[IEEE-830]. Он описывает назначение системы, её функции, категории пользователей, ограничения и детальные требования для первого этапа разработки. Документ предназначен для руководства клуба (заказчика), разработчиков, тестировщиков и технических специалистов, которые будут создавать скрипты анализа.

## Цели

Цель данного документа —  спецификация и согласование требований к программному обеспечению (SRS) для системы аналитики и трекинга футбольных матчей. Главная цель внедряемого продукта — предоставить руководству и владельцам футбольного клуба исчерпывающий набор объективных данных для принятия решений о тренировочном процессе, кадровых перестановках и способах повышения общей производительности команды.

## Границы применения

Программная система предназначена для управления пространственными данными футбольных матчей и их последующего анализа. В границы применения программной системы входят следующие функции:

* Сбор, обработка и хранение данных позиционирования, поступающих с высокоточных датчиков. Данные собираются со стадионных приёмников, считывающих координаты нательных датчиков игроков, игроков команды противника, а также датчика внутри футбольного мяча.
* Генерация "виртуального матча" — трёхмерной визуализации игрового процесса на основе полученного облака точек, точно отражающей взаимное расположение всех участников игры и мяча.
* Инструмент воспроизведения матча (плеер)  с возможностью просмотра игры, игровых моментов и свободным позиционированием виртуальной камеры.
* Разработка и предоставление программного интерфейса (API) для загрузки скриптов и правил расчёта, позволяющих получить неограниченный набор статистических метрик.
Программная система подразумевает работу с готовым потоком данных, в данный документ не входят установка и калибровка физических датчиков и стадионных приёмников. Система является инструментом, облегчающим принятие решений, не принимает решения.

# 2\. Общее описание

## Описание изделия

**Интерфейсы системы**.

* Источник входных данных. Для каждого датчика идентификатор, отметка времени и три координаты. Через этот интерфейс выполняется сбор данных. Протокол передачи данных подлежит уточнению.

**Интерфейсы пользователя**.

* История матчей с поиском и выбором матча для изучения.
* Просмотр виртуального матча, изображение трехмерного поля, участников и мяча, воспроизведение повтора, пауза, перемотка вперед и назад, изменение скорости просмотра, переход к любому моменту матча.
* Управление виртуальной камерой для просмотра игровых моментов с разных сторон.
* Скрипты и статистика. Возможность запустить скрипт для получения статистики каждого игрока за какой-либо временной отрезок (матч/сезон/год). Возможность загрузить в систему правила расчета.
* Подготовка к матчу. Регистрация матча, состава на него и привязка датчиков к игрокам.

**Интерфейсы аппаратных средств ЭВМ**.

* Управляющее устройство приемников. Оборудование, с которым система взаимодействует напрямую, интерфейс передачи данных с приемников в систему подлежит уточнению.
* Рабочее место пользователя должно поддерживать отображение трехмерной графики.
* Хранение данных. Объем хранилища должен быть достаточным для хранения истории матчей.

**Интерфейсы программного обеспечения**.

* ПО приёмников. Получение идентификаторов датчиков, отметок времени и координат.
* ОС. Среда выполнения серверной части приложения.
* Хранилище данных. Хранение точек, истории матчей, результатов расчета.

**Интерфейсы коммуникаций**.

* Канал между приемником и системой (интерфейс передачи данных) подлежит уточнению.
* Локальная сеть. Доступ работников к системе.
* Необходимость удалённого доступа через Интернет подлежит уточнению. При необходимости передача данных должна быть защищена.

**Ограничения памяти**.

* Оперативная память должна обеспечивать воспроизведение виртуального матча и выполнение скриптов; конкретные значения подлежат уточнению.
* Объём постоянной памяти должен быть достаточным для хранения истории матчей. Размер истории матчей подлежит уточнению.

**Действия**.

* Различные способы действий пользователя. Подготовка матча и запись выполняет оператор, обработку после матча - система, анализ - тренерский штаб, аналитики и владелец.
* Периоды диалоговых действий и действий без отклика. Диалоговые: подготовка матча, просмотр, работа со скриптами; без участия пользователя: запись матча, построение виртуального матча.
* Действия системы по копированию данных. Данные матча невозможно получить повторно, необходимо резервное копирование данных для минимизации риска их потери.
* Действия настройки на месте эксплуатации. Указание размеров стадиона, расположение приемников.

## Функции изделия

* **Сохранение данных матча.** Система получает и сохраняет пространственные данные, сформированные на основе показаний датчиков, которые находятся на игроках и мяче.
* **Обработка пространственных данных.** Система обрабатывает полученные данные пространства и связывает их с соответствующими участниками матча, датчиками игроков и мячом для последующей визуализации и анализа.
* **Построение виртуального матча.** На полученных пространственных данных система формирует виртуальное представление футбольного матча, в котором отражены положения игроков и мяча.
* **Воспроизведение матча.** Система предоставляет возможность воспроизводить сохранённый виртуальный матч и отдельно просматривать различные игровые эпизоды.
* **Отображение матча с разных позиций.** Пользователь может просматривать матч, настраивая позицию камеры, ее можно поместить в любую точку полученного пространства и просмотреть игровой момент.
* **Добавление скриптов для анализа.** Пользователь может загрузить любой скрипт с правила расчета для анализа пространственных данных.
* **Составление анализа.** Система предоставляет результаты выполнения скриптов с анализами. Они могут включать, например, среднюю скорость игрока, общее время владения мячом каждого игрока, максимальную скорость какого-то игрока, общее время владения мячом команды, среднее время владения мячом игрока.

## Характеристики пользователей

* **Руководство клуба.** Используют результаты анализа матчей и их визуализацию для получения объективной информации о действиях игроков. На основании предоставленных системой данных могут принимать управленческие решения, связанные с тренировочным процессом, составом команды и повышением её эффективности.
* **Тренеры и спортивные аналитики.** Изучают отдельные игровые эпизоды, положение игроков относительно друг друга и мяча, а также полученные статистические показатели. Пользователи данной категории должны обладать знаниями предметной области футбола и уметь интерпретировать спортивную статистику.
* **Технические специалисты.** Создают и загружают в систему алгоритмы обработки данных матча для расчёта требуемых статистических показателей. Для работы с данной частью системы пользователю необходимы навыки программирования и понимание предоставляемого системой API и структуры пространственных данных.

## Ограничения

* **Рекомендательный характер.** Система не принимает решений; окончательный выбор за тренерами, аналитиками и руководством клуба.
* **Готовый поток данных.** ПО работает с данными от приёмников; установка, калибровка и обслуживание оборудования вне границ продукта.
* **Зависимость от оборудования.** Достоверность виртуального матча и статистики определяется точностью внешнего оборудования и условиями на стадионе.
* **Уточняемые параметры.** Протокол передачи данных, удалённый доступ, объёмы оперативной и постоянной памяти, число одновременных пользователей и скриптов.
* **Поддержка 3D-графики.** Рабочее место пользователя должно поддерживать отображение трёхмерной графики; скорость зависит от вычислительной мощности.
* **Ответственность за скрипты.** За корректность пользовательских скриптов и достоверность результатов отвечает пользователь.
* **Невоспроизводимость данных.** После матча данные нельзя записать повторно; необходимы резервное копирование и достаточное хранилище.
* **Удалённый доступ.** При организации требуется защита передачи и разграничение прав по ролям; также обеспечивается защита от несанкционированного доступа и целостность данных.
* **Соответствие законодательству.** Эксплуатация должна соответствовать законодательству страны, в которой используется система, и применимым нормам, включая защиту персональных данных, интеллектуальную собственность и лицензирование.

## Предположения и зависимости

* Предполагается, что игроки и мяч оснащены исправными датчиками, а по периметру стадиона развёрнуто достаточное число приёмников, обеспечивающих покрытие всей игровой зоны.
* Приёмники стационарны; их расположение не изменяется без повторной калибровки. Датчики на игроках и мяче не снимаются и не смещаются во время матча, а их работе не мешают внешние воздействия.
* Система опирается на ПО приёмников, которое передаёт идентификаторы датчиков, отметки времени и координаты в единой временной шкале матча.
* Подготовка матча выполняется оператором: регистрация матча и состава, привязка датчиков к игрокам.
* Для работы системы необходимы серверная среда выполнения, хранилище данных и рабочее место пользователя с поддержкой трёхмерной графики.
* Доступ сотрудников предполагается через локальную сеть.
* Производительность и объём инфраструктуры должны обеспечивать хранение истории матчей, воспроизведение виртуального матча и выполнение скриптов; конкретные значения уточняются на этапе детального проектирования.
* Предполагаются стабильное электропитание и надёжная сетевая инфраструктура на стадионе и в месте эксплуатации системы, а также достаточное время автономной работы датчиков на протяжении всего матча.
* Внешние компоненты — ПО приёмников, операционная система, СУБД — поддерживаются и обновляются в совместимых версиях; API системы стабилен и документирован.
* Хранилище данных допускает масштабирование по мере накопления истории матчей.
* Пользователи обладают необходимой квалификацией: тренеры и аналитики — в предметной области футбола, технические специалисты — в программировании и работе с API.
* Техническая поддержка и обновление ПО осуществляются в рамках отдельного регламента; условия и сроки уточняются.

# 3\. Детальные требования

## Функциональные требования

* **Первоначальная настройка и конфигурирование** Система предоставляет возможность указать источник потока данных для построения облака точек, положение поля в пространстве, путь и параметры подключения к хранилищу данных (СУБД).
* **Подготовка к матчу** Система позволяет оператору перед началом игры зарегистрировать новый матч, внести составы команд, выполнить привязку 110 датчиков к игрокам, а также запустить и остановить запись матча.
* **Приём и сохранение данных** Во время записи матча система в реальном времени принимает поток данных (id датчика, timestamp, x, y, z) со скоростью не менее 1110 сообщений в секунду и сохраняет полученное облако точек в СУБД в сжатом виде.
* **Обработка данных** Система в фоновом режиме (без блокировки работы пользователя) связывает полученные пространственные данные (координаты) с профилями игроков и мячом, формируя на их основе трёхмерную реконструкцию игры.
* **История матчей** Система ведёт архив записанных матчей и результатов расчётов. Пользователю предоставляется интерфейс для просмотра списка матчей, поиска матчей по заданным фильтрам (временной период, команда противника, результат матча) для дальнейшего просмотра и анализа.
* **Просмотр виртуального матча (плеер)** Система отображает трёхмерную модель поля, положения игроков и мяча и предоставляет интерактивные элементы управления воспроизведением: пуск, паузу, перемотку вперёд и назад, изменение скорости просмотра (0.5x; 1x; 1.5x; 2x), быстрый переход в нужный момент по временной шкале, возможность вырезать и просмотреть определённый момент или отрезок матча. Пользователю также предоставляется свободное управление виртуальной камерой, с возможностью просмотра виртуального матча с любой точки трёхмерного пространства.
* **Загрузка и выполнение аналитических скриптов** Система предоставляет документрированный API для загрузки пользовательских скриптов с правилами расчёта. При запуске скрипта система передаёт ему доступ к записанному облаку точек, выполняет расчёт и отображает полученную статистику по каждому игроку и среднее по команде в целом.
* **Права доступа** Доступ к функциям системы осуществялется с разделением прав по ролям: оператор (настройка и запись матча), тренеры и спортивные аналитики (просмотр матчей, запуск скриптов и просмотр статистики), технические специалисты (загрузка разработанных скриптов через API) и руководство клуба (просмотр статистики и визуализаций).
* **Мониторинг и обработка пользовательских ошибок** Система ведёт журнал событий, контролирует очередь обработки, соединение с приёмниками и загрузку ресурсов (ЦП, ОЗУ, GPU, диск), а также выводит понятные уведомления пользователю при возникновении сбоев.

## Надежность

* **Доступность** Коэффициент доступности системы во время проведения матчей, тренировок и рабочего времени аналитического штаба должен составлять не менее 99,50%. Плановые обновления ПО (с простоем не более 10 минут) должны проводиться строго вне времени матчей.
* **MTBF** Среднее время безотказной работы серверной части системы между сбоями должно составлять не менее 500 часов.
* **MTTR**:  Среднее время восстановления работоспособности системы после программного сбоя не должно превышать 1 час.
* **Точность** Система должна обеспечивать приём и запись потока из 1110 сообщений от датчиков в секунду (с точностью не хуже 5мм), сохранять исходную точность пространственных данных при вычислениях с учётом погрешностей округления
* **Макс. количество ошибок** Для системы не допускается более 2 ошибок в месяц, приводящих к простою системы более 30 минут. Ошибки, приводящие к безвозвратной потере важных данных (облака точек записанного матча) не допускаются.

## Производительность

* **Время отклика.** Интерактивные операции — пауза, перемотка, смена скорости, перемещение виртуальной камеры — выполняются с задержкой не более 100 мс. Запуск аналитического скрипта и получение первых результатов — в пределах 5 секунд. Построение виртуального матча ведётся в фоновом режиме и не блокирует работу пользователя. Загрузка матча из истории до готовности к воспроизведению — не более 3 секунд.
* **Пропускная способность.** Система принимает и обрабатывает поток пространственных данных от приёмников без потерь — не менее 1110 сообщений в секунду (111 датчиков ? 10 Гц: 22 игрока ? 5 датчиков и 1 датчик в мяче). Точность определения координат — не хуже 5 мм. Заложенный резерв пропускной способности — не менее 30% на случай расширения состава оборудования.
* **Утилизация ресурсов.** Система эффективно распределяет вычислительные ресурсы, не допуская перегрузок, ведущих к деградации быстродействия: загрузка ЦП — до 80%, ОЗУ — до 80%, GPU — до 90%. Скорость последовательной записи на диск — не менее 100 МБ/с, что обеспечивает сохранение потока в реальном времени. Объём данных одного матча продолжительностью 90 минут — 0,8–1,2 ГБ в сжатом виде.
* **Плавность визуализации.** Воспроизведение виртуального матча обеспечивает стабильные 30 FPS при разрешении 1920?1080 и 60 FPS при 1280?720. Задержка отклика виртуальной камеры на действия пользователя — не более 10 мс, что обеспечивает естественное восприятие движения.
* **Задержка публикации данных.** Медианная задержка от сбора данных приёмниками до их доступности в системе не должна превышать 300 мс. Такой порог обеспечивает построение виртуального матча практически в реальном времени и комфортную работу пользователей без ощущения отставания от хода игры.
* **Масштабирование и поиск.** Хранилище масштабируется по мере накопления истории матчей без остановки системы. Поиск матча по заданным критериям занимает не более 2 секунд при архиве до 1000 матчей.



## Ремонтопригодность

* **Модульность.** Система построена из функционально обособленных модулей — сбор данных, обработка, визуализация, API, интерфейс, администрирование. Взаимодействие между ними осуществляется через документированные интерфейсы, что упрощает замену и обновление отдельных компонентов.
* **Диагностика.** Система ведёт журнал событий с уровнями важности и отслеживает ключевые показатели: загрузку ЦП, ОЗУ, GPU, диска, состояние приёмников и очередей обработки. При выходе за допустимые пределы формируется предупреждение — это позволяет устранить проблему до сбоя.
* **Обновление и восстановление.** Обновление ПО производится с простоем не более 10 минут и возможностью отката к предыдущей версии. Средняя наработка на отказ (MTBF) — не менее 400 часов, среднее время восстановления (MTTR) — не более 30 минут. Целевое время восстановления после сбоя (RTO) — не более 4 часов, точка восстановления данных (RPO) — не более 15 минут.
* **Резервное копирование.** Пространственные данные матча невозможно получить повторно, поэтому резервное копирование выполняется автоматически — не реже раза в сутки, с глубиной хранения не менее 30 дней. Срок хранения пространственных данных — не менее 3 лет с возможностью продления.
* **Документация.** Техническая документация — архитектурное описание, руководство администратора, описание API, инструкции по развёртыванию и обновлению — поддерживается в актуальном состоянии и обновляется при изменении системы.
* **Тестирование.** Предусмотрены автоматизированные модульные, интеграционные и нагрузочные тесты. Рекомендуется использование CI/CD, статического анализа и код-ревью для снижения риска регрессий.
* **Конфигурирование.** Ключевые параметры — пути к данным, подключение к СУБД, частота опроса, параметры стадиона — задаются через конфигурационные файлы или переменные окружения без изменения программного кода.
* **Совместимость и поддержка версий.** Серверная часть работает под управлением Linux (дистрибутив уточняется). Клиентское рабочее место может быть реализовано на Windows или Linux при условии поддержки трёхмерной графики. API аналитических скриптов обновляется с сохранением обратной совместимости: поддерживаются текущая и две предыдущие версии, период поддержки — не менее 12 месяцев после выпуска новой версии.
* **Учёт инцидентов.** Все инциденты с простоем системы фиксируются с указанием времени обнаружения, восстановления и первопричины. Целевой показатель — не более 2 инцидентов в месяц с простоем более 30 минут.



## Ограничения проекта

**Границы программного продукта.** Разрабатывается программная система для получения, хранения, обработки и визуализации пространственных данных футбольного матча и выполнения пользовательских скриптов для анализа. Разработка, установка, калибровка и обслуживание физических датчиков и приемников в проект не входит.
**Скорость поступления данных.** Данные от приемников поступают с частотой 10 измерений в секунду. Для данного количества датчиков система должна быть рассчитана на прием 1110 сообщений в секунду.
**Ограничения среды выполнения.** Серверная часть системы должна функционировать под управлением любом из поддерживаемых операционных систем семейства Linux. Конкретный дистрибутив подлежит уточнению.
**Использование СУБД.** Для хранения пространственных данных, истории матчей и результатов обработки данных система должна использовать СУБД. Требуемый объём и конкретная СУБД подлежат уточнению.
**Пользовательский интерфейс.** Рабочее место пользователя должно обладать возможностями для поддержки 3D-графики и воспроизведения виртуального матча.
**Ограничения аналитических скриптов.** Система должна предоставлять API для загрузки и запуска скриптов, которым должен предоставляться доступ к облаку точек выбранного матча или периода. Язык скриптов и формат результатов подлежат уточнению.
**Сетевое ограничение.** Доступ сотрудников к системе производится через локальную сеть. Предоставление удаленного доступа через интернет не предусмотрено.
**Сохранение данных.** Пространственные данные завершенного матча невозможно получить повторно, поэтому проект должен предусматривать их надежное хранение и резервное копирование.
**Ограничения на результаты системы.** Система предоставляет пользователям визуализацию, статистические показатели и результаты аналитических скриптов, но не принимает решения о тренировочном процессе или составе команды самостоятельно.
**Законодательные и лицензионные соглашения.** При реализации системы должны учитываться требования законодательства, связанные с обработкой и хранением данных, защитой информации, интеллектуальной собственностью и лицензированием используемых программных компонентов.



## Требования к пользовательской документации

Пользовательская документация должна предусматривать использование системы всеми возможными категориями пользователей и учитывать их уровень технических навыков и выполняемые задачи.
Пользовательская документация должна включать:

* **Руководство подготовки к матчу.** Должно включать порядок подготовки к матчу: регистрацию матча, указание состава команды, установление датчиков на игроков, запуск и завершение записи данных.
* **Руководство по работе с историей матча.** Должно описывать поиск и выбор сохраненного матча, открытие виртуального матча и работу с сохраненными данными.
* **Руководство по просмотру виртуального матча.** Должно описывать управление воспроизведением: запуск, паузу, перемотку назад и вперед, изменение скорости воспроизведения и переход к выбранному моменту матча.
* **Руководство по работе с виртуальной камерой.** Должно описывать изменение положения виртуальной камеры и возможность просмотра с различных ракурсов.
* **Руководство для тренеров и спортивных аналитиков.** Должно описывать просмотр игровых эпизодов, выполнение аналитических скриптов и получение статистических результатов для каждого игрока и команды в целом.
* **Руководство по разработке аналитических скриптов.** Должно содержать порядок создания, загрузки и запуска пользовательских скриптов, описание доступных входных данных и требований к возвращаемым результатам.
* **Инструкция по первоначальной настройке системы.** Должна содержать описание параметров, задаваемых на месте эксплуатации системы, включая размеры стадиона, расположение приёмников, подключение к ПО приёмников, СУБД и другим необходимым компонентам.
* **Описание типовых ошибок.** Документация должна содержать рекомендации по действиям пользователя при отсутствии данных от приёмников, невозможности воспроизвести матч, ошибке выполнения аналитического скрипта и других типовых сбоях пользовательских операций.
* **Требования к актуальности документации.** Пользовательская документация должна обновляться при изменении пользовательского интерфейса, API, формата входных данных, порядка подготовки матча или правил выполнения аналитических скриптов.

## Применимые стандарты

* \[152-ФЗ] «О персональных данных». Данные о перемещениях конкретного игрока являются его персональными данными. Их сбор, хранение и обработка, в том числе по игрокам команды соперника, должны соответствовать этому закону, а доступ к ним разрешается только пользователям системы в соответствии с их ролями.
* \[ГОСТ 8.417] «Единицы величин». Координаты, время и скорость в интерфейсе, API скриптов и результатах анализа выражаются в единицах СИ: метры, секунды (миллисекунды), м/с.Индекс
