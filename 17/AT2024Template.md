# 1. Введение
[Обзор всего документа SRS.]

## Цели
Целью настоящего документа является определение функциональных и нефункциональных требований к системе «PeerReview» — программному обеспечению для организации взаимной проверки (peer review) практических работ студентов в рамках курса преподавателя с использованием механизмов калибровочного контроля и автоматического выделения доверенных рецензентов.

Аудитория документа:
- заказчик — преподаватель и администрация вуза
- команда разработки и проектирования
- тестировщики
- сопровождающие специалисты ИТ-подразделения вуза

## Границы применения
PeerReview – веб-система, которая автоматизирует взаимное оценивание работ студентов в рамках практических занятий и снижает нагрузку преподавателя на проверку. Система позволяет преподавателю создавать задания, а студентам загружать работы и рецензировать чужие, также она автоматически распределяет работы между рецензентами и выявляет конфликтные работы, чтобы направить преподавателю на перепроверку.

Система распространяется на:
- управление курсами и заданиями;
- импорт списков студентов и преподавателей из кадровой системы вуза;
- загрузку студенческих работ;
- формирование калибровочной выборки работ для личной проверки преподавателем;
- автоматическое присвоение студентам статуса «студент-эксперт» на основе успеваемости и совпадения оценок с эталоном преподавателя;
- автоматическое распределение работ между n рецензентами (с приоритетным включением студента-эксперта), исключая самопроверку и обеспечивая анонимность;
- выставление рецензий и оценок студентами;
- агрегацию оценок и выявление работ, где средняя оценка студентов расходится с оценкой эксперта выше порога d;
- ручную перепроверку конфликтных работ преподавателем;
- экспорт итоговых ведомостей;
- аутентификацию через SSO вуза;
- рассылку уведомлений через почтовый сервер вуза.

Система не распространяется на:
- учётные системы вуза (расписание, учебные планы, итоговые ведомости);
- автоматическую проверку содержимого работ, оценивание выполняют люди;
- самостоятельную регистрацию пользователей, учётные записи импортируются извне;
- сканирование и оцифровку работ, студент загружает готовый файл;
- защиту от сговора рецензентов - это организационная мера преподавателя.

# 2. Общее описание

## Описание изделия
Система «PeerReview» является самостоятельным веб-приложением, входящим в ИТ-инфраструктуру вуза. Система взаимодействует с внешними информационными системами вуза и использует их данные и сервисы для обеспечения своей работы.

- **Интерфейсы системы**:
   - кадровая система вуза — импорт списков студентов и преподавателей
   - служба аутентификации вуза — SSO
   - почтовый сервер вуза — рассылка уведомлений

- **Интерфейсы пользователя**:
   - кабинет студента
   - кабинет преподавателя
   - кабинет администратора

- **Интерфейсы аппаратных средств ЭВМ**:
   - специализированное аппаратное обеспечение не требуется
   - сервер: не менее 4 CPU, 8 ГБ RAM, 500 ГБ дискового пространства
   - клиентские устройства — ПК и мобильные устройства с браузером

- **Интерфейсы программного обеспечения**:
   - Linux
   - PostgreSQL 14+
   - nginx
   - браузеры Chrome, Firefox, Edge, Safari

- **Интерфейсы коммуникаций**:
   - HTTPS/TLS 1.2+
   - REST/JSON
   - SMTP (STARTTLS)
   - LDAP / SAML 2.0 / OpenID Connect

- **Ограничения памяти**:
   - максимальный размер одной загружаемой работы — 20 МБ
   - суммарно на студента по одному заданию — не более 50 МБ
   - оценка необходимого хранилища — около 200 ГБ, с резервными копиями — 500 ГБ

- **Действия**:
   - обычный цикл работы системы (регистрация курсов, загрузка работ, настройка преподавателем калибровочной квоты K)
   - периодические операции (накопительный анализ истории проверок, оценка успеваемости, расчет сходимости с преподавателем и автоматическое обновление статуса "Студент-эксперт")
   - операции после дедлайна (извлечение случайных работ для проверки преподавателем, распределение остальных работ с обязательным включением эксперта в каждую группу студентов, автоматический расчет оценок и выявление конфликтов по порогу d)
   - действия при авариях (сбои при импорте из кадровой системы, отказы SSO)

## Функции изделия
Ниже приведено резюме основных функций системы, которые сгруппированы по ролям.

Преподаватель:
- создание курса и заданий;
- настройка параметров оценивания(n, шкала, квота работ для калибровки K_prof, пороги G_exp, δ_exp, d);
- личная проверка калибровочной выборки работ для формирования эталонных оценок;
- просмотр конфликтных работ(и работ с расхождением с оценкой эксперта) и вынесение итоговой оценки;
- экспорт итоговой ведомости.

Студент:
- загрузка работы в рамках задания;
- просмотр работ, назначенных на рецензирование;
- выставление оценки и комментария;
- получение статуса «студент-эксперт» и выполнение проверок в этом статусе;
- просмотр итоговой оценки по своей работе.

Система (автоматически):
- отбор калибровочной выборки работ для преподавателя;
- анализ сходимости оценок студентов с оценками преподавателя и присвоение статуса эксперта;
- распределение работ между n рецензентами(с назначением хотя бы одного эксперта на работу, если это возможно);
- агрегация оценок и сравнение средней оценки сокурсников с оценкой эксперта(расчёт разности Δ);
- направление конфликтных работ(Δ > d) и работ без проверки эксперта преподавателю;
- рассылка уведомлений.

Администратор:
- импорт списков студентов и преподавателей из инфраструктуры вуза;
- управление правами доступа;
- резервное копирование и мониторинг инцидентов.

Общее:
- аутентификация через SSO вуза;
- разграничение прав по ролям;
- обработка персональных данных в соответствии с [FZ-152].

## Характеристики пользователей
1. **Студент**:
   - **Квалификация и навыки**: базовый уровень компьютерной грамотности (умение работать с веб-браузером, загружать файлы, следовать текстовым инструкциям). Специальной подготовки по работе с ПО не требуется.
   - **Образовательный уровень**: студенты вуза (бакалавриат, специалитет, магистратура).
   - **Опыт работы в системе**: периодическое использование в рамках выполнения учебного плана семестра.
   - **Задачи**: вход в систему через учетную запись SSO вуза; своевременная загрузка файлов практических заданий строго до наступления дедлайна сдачи; просмотр назначенных на взаимное рецензирование работ сокурсников, выставление баллов и рецензий по заданным критериям до дедлайна проверки; получение системного статуса «студент-эксперт» при условии высокой собственной успеваемости и стабильной сходимости выставляемых оценок с эталонными оценками преподавателя; просмотр итоговых оценок и рецензий по своим работам.

2. **Преподаватель**:
   - **Квалификация и навыки**: уверенный пользователь ПК.
   - **Образовательный уровень**: высшее образование, профильная квалификация в предметной области курса.
   - **Опыт работы в системе**: регулярное использование в течение учебного курса.
   - **Задачи**: настройка параметров оценивания курса (число рецензентов n, квота случайно отбираемых работ для личной калибровочной проверки K_prof, доверительный порог сходимости δ_exp и порог успеваемости G_exp для присвоения статуса эксперта, порог допустимого расхождения средней оценки с оценкой эксперта d); проведение калибровочной проверки отобранных системой работ; ручной арбитраж работ, где средний балл сокурсников разошелся с оценкой эксперта выше порога d, а также работ, не проверенных в установленный срок; модерация процесса оценивания, экспорт итоговой ведомости.

3. **Администратор системы**:
   - **Квалификация и навыки**: квалифицированный технический специалист, знающий основы администрирования веб-систем и баз данных.
   - **Задачи**: настройка и мониторинг интеграции с кадровой системой вуза ([KADR]) для импорта списков студентов и преподавателей, обеспечение взаимодействия со службой внешней аутентификации (SSO), управление правами доступа, резервное копирование и решение технических инцидентов.

## Ограничения
1. **Методологические ограничения оценивания и роль экспертов**:
   - Процесс взаимной проверки должен быть строго двусторонне анонимным: проверяющий не имеет доступа к данным об авторе работы, автор не видит персональные данные рецензентов, а статус эксперта не раскрывается сокурсникам.
   - Алгоритм распределения обязан полностью исключать самопроверку: студент ни при каких условиях не назначается рецензентом собственной работы.
   - Калибровка оценок: система формирует случайную выборку работ в объеме K_prof, заданном преподавателем, для его личной проверки и фиксации эталонных оценок.
   - Статус эксперта: система динамически присваивает статус «студент-эксперт» тем обучающимся, чей средний балл за собственные работы не ниже заданного порога G_exp (по умолчанию ≥ 4.0), а выставленные оценки статистически совпадают с эталонами преподавателя в пределах доверительного интервала δ_exp.
   - Формирование группы рецензентов: алгоритм распределения обязан по возможности включать не менее одного студента со статусом «эксперт» в число n рецензентов каждой работы.
   - Триггер ручного арбитража: если средний арифметический балл сокурсников существенно отклоняется от оценки назначенного эксперта (разница превышает установленный порог d), автоматическое выставление оценки блокируется, и работа передается на проверку преподавателю.

2. **Интеграционные зависимости**:
   - Система не является первичным источником учетных записей и не предусматривает самостоятельную открытую регистрацию; реестры студентов, преподавателей и учебных групп импортируются из кадровой системы вуза ([KADR]).

3. **Конфигурируемость правил проверки**:
   - Все параметры алгоритма (число рецензентов n, квота работ для калибровки преподавателем K_prof, порог успеваемости G_exp и доверительный интервал δ_exp для экспертов, критический порог расхождения с оценкой эксперта d) должны настраиваться преподавателем индивидуально для каждого задания через интерфейс без изменения программного кода.

4. **Нормативные требования и безопасность**:
   - Хранение и обработка персональных данных участников должны строго соответствовать требованиям законодательства РФ ([FZ-152]).

5. **Режим дедлайнов**:
   - Загрузка работ и сдача рецензий ограничены жесткими временными рамками; отправка решений после наступления дедлайна сдачи блокируется, а при срыве дедлайна проверки рецензентом работа автоматически перенаправляется преподавателю.

6. **Внешняя аутентификация**:
   - Система не хранит пароли пользователей и не ведет локальную базу учетных записей; аутентификация выполняется исключительно через службу SSO вуза.

## Предположения и зависимости
- Кадровая система вуза предоставляет корректные списки ([KADR]).
- У каждого студента есть учётная запись вуза, интернет и e-mail.
- На задании сдано не менее n + 1 работ (иначе FR-5.4).
- За семестр заданий достаточно много (порядка 10 и более), чтобы накопить m_min сравнений с преподавателем и выявить экспертов. Для короткого курса экспертов может не оказаться.
- Преподаватель успевает проверять контрольную выборку и очередь расхождений.
- Контрольная выборка по заданию достаточно велика, чтобы за семестр у каждого студента набиралось сравнений (TBD-2: расчёт минимального k).
- Вуз допускает взаимную оценку студентов.

# 3. Детальные требования

## Функциональные требования

Каждое функциональное требование имеет уникальный идентификатор вида `FR-x.y` и приоритет реализации: **О** — обязательное требование, **Ж** — желательное требование.

##### 1. Аутентификация и управление пользователями

- **FR-1.1 (Приоритет: О) — Аутентификация через SSO вуза**
  * **Описание**: Система должна обеспечивать вход пользователей (студентов, преподавателей, администраторов) исключительно через внешнюю службу единой аутентификации вуза ([SSO]: LDAP / SAML 2.0 / OpenID Connect). Самостоятельная регистрация пользователей в Системе не допускается.
  * **Входные данные**: Учётные данные пользователя, переданные провайдером SSO, и токен сессии.
  * **Обработка и проверка**: Система проверяет валидность токена SSO и сопоставляет идентификатор пользователя с локальным реестром учётных записей.
  * **Выходные данные**: Авторизованная сессия и перенаправление в личный кабинет в соответствии с ролью (кабинет студента, преподавателя или администратора).
  * **Нештатные ситуации**: При невалидном токене или отсутствии пользователя в реестре Система отказывает в доступе и выводит сообщение об ошибке авторизации.

- **FR-1.2 (Приоритет: О) — Импорт списков пользователей из кадровой системы вуза**
  * **Описание**: Система должна позволять Администратору выполнять импорт и синхронизацию актуальных списков студентов, учебных групп и преподавателей из кадровой системы вуза ([KADR]).
  * **Входные данные**: Пакет данных из внешней системы по API (REST/JSON) либо файл выгрузки установленного формата.
  * **Обработка и проверка**: Система проверяет целостность структуры данных, уникальность идентификаторов и наличие обязательных полей (ФИО, роль, учебная группа, адрес электронной почты).
  * **Выходные данные**: Обновлённый реестр пользователей и групп в базе данных PostgreSQL, запись в журнале событий о результатах синхронизации.
  * **Нештатные ситуации**: При недоступности внешней системы или ошибке формата данных транзакция откатывается, сохраняется предыдущее состояние реестра, а Администратору выводится диагностическое сообщение об ошибке.

- **FR-1.3 (Приоритет: О) — Разграничение прав доступа по ролям**
  * **Описание**: Система должна разграничивать доступ к функциям и данным в соответствии с назначенной ролью пользователя («Студент», «Преподаватель», «Администратор») и позволять Администратору управлять правами доступа.
  * **Нештатные ситуации**: При попытке обращения к функции или странице, не разрешённой для текущей роли, Система блокирует операцию и возвращает ошибку доступа (HTTP 403).

##### 2. Управление курсами и практическими заданиями

- **FR-2.1 (Приоритет: О) — Создание и редактирование учебного курса**
  * **Описание**: Система должна позволять Преподавателю создавать учебный курс и привязывать к нему учебные группы студентов из импортированного реестра.
  * **Входные данные**: Название курса, описание, список прикреплённых учебных групп.
  * **Выходные данные**: Созданная карточка курса, доступная студентам выбранных групп.

- **FR-2.2 (Приоритет: О) — Создание задания и настройка параметров взаимного оценивания**
  * **Описание**: Система должна позволять Преподавателю создавать в рамках курса практическое задание и настраивать параметры взаимного рецензирования, калибровки и выявления экспертов.
  * **Входные данные**:
    * название и текстовое описание задания (критерии оценки);
    * дедлайн сдачи работ студентами (T_submit);
    * дедлайн выполнения взаимного рецензирования (T_review, где T_review > T_submit);
    * шкала оценивания (диапазон допустимых баллов);
    * число рецензентов на одну работу n (целое число, n ≥ 1);
    * квота работ для калибровочной проверки преподавателем K_prof (целое неотрицательное число или процент от сданных работ);
    * порог успеваемости студента для роли эксперта G_exp (по умолчанию ≥ 4.0);
    * доверительный порог сходимости оценок студента с эталоном преподавателя δ_exp;
    * критический порог допустимого расхождения между средней оценкой рецензентов и оценкой студента-эксперта d (d ≥ 0).
  * **Обработка и проверка**: Система проверяет корректность введённых значений (n ≥ 1, d ≥ 0, G_exp ≥ 0, δ_exp ≥ 0, а также то, что дата T_review наступает позже T_submit).
  * **Выходные данные**: Опубликованное задание со статусом «Открыт приём работ».
  * **Нештатные ситуации**: При вводе некорректных параметров Система запрещает сохранение задания и подсвечивает поля с ошибками.

##### 3. Загрузка студенческих работ

- **FR-3.1 (Приоритет: О) — Загрузка файлов практической работы**
  * **Описание**: Система должна позволять Студенту загружать файл (или несколько файлов) выполненной практической работы по открытому заданию курса до наступления дедлайна T_submit.
  * **Входные данные**: Файл(ы) работы, загружаемые через веб-интерфейс кабинета студента.
  * **Обработка и проверка**:
    * проверка того, что текущее серверное время не превышает дедлайн сдачи T_submit;
    * проверка размера: размер одного файла не должен превышать 20 МБ, а суммарный объём файлов одного студента по одному заданию — не более 50 МБ;
    * при загрузке новой версии до дедлайна предыдущая версия работы перезаписывается;
    * сохранение работы с привязкой к внутреннему идентификатору Автора без отображения его ПДн в интерфейсе проверки.
  * **Выходные данные**: Сохранённая работа со статусом «Сдана» и уведомление об успешной загрузке.
  * **Нештатные ситуации**: При превышении лимита 20 МБ на файл или 50 МБ суммарно Система отклоняет загрузку и выводит сообщение о превышении допустимого объёма.

- **FR-3.2 (Приоритет: О) — Блокировка приёма работ после дедлайна**
  * **Описание**: После наступления дедлайна сдачи T_submit Система должна автоматически прекращать приём и обновление работ по заданию. Работы, не загруженные до T_submit, не принимаются и не засчитываются.

##### 4. Формирование пула экспертов и распределение работ

- **FR-4.1 (Приоритет: О) — Отбор калибровочной выборки преподавателя**
  * **Описание**: После наступления дедлайна сдачи T_submit Система должна автоматически формировать случайную выборку работ в объёме K_prof, назначенных для личной оценки Преподавателем.
  * **Входные данные**: Множество всех сданных работ M и параметр квоты K_prof.
  * **Обработка и проверка**: Выборка формируется генератором псевдослучайных чисел; отобранные работы получают метку «Калибровочная выборка» и направляются в кабинет Преподавателя. Оценки преподавателя фиксируются в системе как эталонные.
  * **Выходные данные**: Список работ в очереди личной проверки Преподавателя.

- **FR-4.2 (Приоритет: О) — Динамическое присвоение статуса «Студент-эксперт»**
  * **Описание**: Система должна анализировать историю выполнения и проверки работ студентами и автоматически присваивать признак «Студент-эксперт» тем пользователям, которые удовлетворяют критериям надежности.
  * **Входные данные**: История оценок автора за собственные сданные работы, архив выставленных им оценок по калибровочным работам, эталонные оценки Преподавателя, параметры G_exp и δ_exp.
  * **Обработка и проверка**:
    * проверка успеваемости: средний балл студента за его собственные сданные работы должен быть не ниже порога G_exp (по умолчанию ≥ 4.0);
    * проверка сходимости: абсолютная разность между оценкой данного студента и эталоном Преподавателя по калибровочным работам не должна превышать порог δ_exp в статистически преобладающем числе случаев.
  * **Выходные данные**: Присвоение профилю студента системного статуса «Студент-эксперт».

- **FR-4.3 (Приоритет: О) — Распределение работ с обязательным назначением студента-эксперта**
  * **Описание**: Система должна распределять сданные работы между рецензентами с обязательным включением в состав проверяющих доверенного эксперта при сохранении взаимной анонимности.
  * **Входные данные**: Множество сданных работ M, параметр n, реестр подтвержденных студентов-экспертов.
  * **Обработка и проверка**:
    * проверка условия достаточности: общее количество сданных работ |M| ≥ n + 1;
    * для каждой работы в группу из n рецензентов алгоритм в приоритетном порядке назначает одного студента со статусом «Студент-эксперт»;
    * остальные n - 1 рецензентов назначаются случайным образом с обеспечением равномерной нагрузки;
    * **исключение самопроверки**: Автор работы не может быть назначен её Рецензентом;
    * **двусторонняя анонимность**: Система скрывает персональные данные Автора от Рецензентов, данные Рецензентов от Автора, а также не раскрывает сокурсникам факт наличия статуса эксперта у проверяющего.
  * **Выходные данные**: Сформированные назначения на рецензирование в кабинетах студентов.
  * **Нештатные ситуации**:
    * если |M| < n + 1, распределение отменяется, все работы направляются Преподавателю;
    * если в потоке недостаточно подтвержденных студентов-экспертов, Система распределяет работы случайным образом среди доступных студентов и отправляет уведомление Преподавателю.

##### 5. Взаимное рецензирование работ студентами

- **FR-5.1 (Приоритет: О) — Просмотр назначенных работ и выставление рецензии**
  * **Описание**: Система должна предоставлять Студенту-рецензенту доступ к скачиванию/просмотру обезличенных файлов назначенных ему работ и форму для выставления оценки и текстового комментария до дедлайна T_review.
  * **Входные данные**: Числовая оценка в пределах заданной шкалы задания и (опционально) текстовый комментарий.
  * **Обработка и проверка**: Проверка вхождения оценки в допустимый диапазон шкалы задания и проверка того, что текущее время не превышает дедлайн T_review.
  * **Выходные данные**: Сохранённая обезличенная Рецензия в базе данных.
  * **Нештатные ситуации**: При попытке ввести балл вне диапазона шкалы или отправить рецензию после наступления T_review Система отклоняет сохранение и выводит сообщение об ошибке.

- **FR-5.2 (Приоритет: Ж) — Фиксация просрочек и переназначение непроверенных работ**
  * **Описание**: Система должна фиксировать факт невыполнения рецензентом проверки в установленный срок и предоставлять возможность автоматического переназначения работы другому рецензенту (включая резервного эксперта) до истечения этапа проверки.

##### 6. Агрегация оценок, валидация через эксперта и арбитраж

- **FR-6.1 (Приоритет: О) — Валидация оценок через эксперта и выставление итогового балла**
  * **Описание**: После получения всех рецензий по работе Система сопоставляет оценки рядовых рецензентов с оценкой назначенного студента-эксперта.
  * **Входные данные**: Набор оценок сокурсников {g_1, g_2, ..., g_{n-1}}, оценка назначенного студента-эксперта g_exp и порог расхождения d.
  * **Обработка и проверка**:
    * Система вычисляет средний арифметический балл рецензентов-сокурсников: G_peer = (g_1 + g_2 + ... + g_{n-1}) / (n - 1);
    * Система рассчитывает абсолютную разность между средним баллом сокурсников и оценкой эксперта: Δ = |G_peer - g_exp|;
    * если Δ ≤ d, оценки считаются согласованными, и итоговой оценкой назначается средний балл по всей группе рецензентов (включая эксперта): G_final = (G_peer * (n - 1) + g_exp) / n;
    * работе присваивается статус «Проверена автоматически».
  * **Выходные данные**: Зафиксированная итоговая оценка G_final, доступная Автору в личном кабинете вместе с обезличенными рецензиями.

- **FR-6.2 (Приоритет: О) — Направление конфликтных и недопроверенных работ Преподавателю**
  * **Описание**: Система должна автоматически направлять работу в очередь на ручной арбитраж Преподавателю в следующих случаях:
    1. Расхождение между оценкой сокурсников и оценкой студента-эксперта превышает установленный порог (Δ > d).
    2. Наступил дедлайн рецензирования T_review, но хотя бы один из назначенных рецензентов не выставил оценку вовремя (включая случай отсутствия рецензии от эксперта).
    3. В группу рецензентов данной работы не удалось назначить студента-эксперта из-за нехватки подтвержденных экспертов на курсе.
  * **Выходные данные**: Работа получает статус «Требует проверки преподавателя» и помещается в очередь арбитража в кабинете Преподавателя.

- **FR-6.3 (Приоритет: О) — Ручная перепроверка и арбитраж Преподавателем**
  * **Описание**: Система должна позволять Преподавателю просматривать работы из очереди калибровки и арбитража (файлы решения, выставленные баллы и комментарии) и выносить окончательное решение.
  * **Входные данные**: Окончательная оценка Преподавателя по шкале задания и текстовый комментарий (опционально).
  * **Выходные данные**: Зафиксированная итоговая оценка Преподавателя (имеющая абсолютный приоритет над оценками студентов), статус работы меняется на «Проверена преподавателем». Эталонная оценка сохраняется в базе для последующей калибровки рецензентов.

##### 7. Уведомления и отчётность

- **FR-7.1 (Приоритет: О) — Экспорт итоговой ведомости**
  * **Описание**: Система должна позволять Преподавателю экспортировать итоговую ведомость оценок по заданию или курсу в табличных форматах CSV и XLSX.
  * **Выходные данные**: Сформированный файл CSV / XLSX, содержащий список студентов группы, статус сдачи работы, оценки рецензентов, оценку эксперта, признак расхождения Δ, итоговый балл и способ его выставления (автоматически / преподавателем).

- **FR-7.2 (Приоритет: О) — Рассылка уведомлений по электронной почте**
  * **Описание**: Система должна автоматически отправлять уведомления через почтовый сервер вуза по протоколу SMTP (STARTTLS) при наступлении следующих событий:
    * назначение работ на рецензирование студенту;
    * присвоение студенту статуса эксперта;
    * приближение дедлайна сдачи или рецензирования (напоминание);
    * поступление калибровочной или конфликтной работы в очередь преподавателю;
    * выставление итоговой оценки по работе студента.
  * **Нештатные ситуации**: При временной недоступности почтового сервера ошибка фиксируется в системном журнале, а сообщение ставится в очередь повторной отправки без блокировки основной операции.

## Надежность

- **Доступность**: 99 % в течение учебного семестра (допускаются плановые работы в непиковые дни).
- **MTBF**: Не менее 720 часов (30 дней) непрерывной работы между критическими сбоями.
- **MTTR**: Не более 4 часов в обычное время и не более 1 часа в период дедлайнов.
- **Точность**: Расчёт среднего арифметического балла и абсолютной величины расхождения Δ с оценкой студента-эксперта выполняется с математической точностью до 0,01 балла.
- **Макс. количество ошибок**: Не более 3 критических дефектов, блокирующих основной функционал (загрузку работ, рецензирование, расчёт итоговых оценок), на момент релиза.

## Производительность

Все требования к производительности указаны из расчёта работы Системы на базовой аппаратной конфигурации сервера, определённой в разделе 2.1 (не менее 4 ядер CPU, 8 ГБ RAM, 500 ГБ дискового пространства, сетевой канал не менее 100 Мбит/с).

- **PR-1 (Приоритет: О) — Время отклика**:
  * **Типовые веб-запросы и операции с данными** (открытие страниц личного кабинета, просмотр списка заданий, сохранение оценки и комментария рецензии):
    * не менее 95 % запросов должны обрабатываться Системой менее чем за **1,5 с** при штатной нагрузке;
    * 100 % запросов должны обрабатываться не дольше **3,0 с** при пиковой нагрузке (в последние 30 минут перед наступлением дедлайна).
  * **Загрузка и скачивание файлов работ** (размером до 20 МБ при скорости клиентского соединения не менее 20 Мбит/с):
    * 95 % операций загрузки/скачивания файла должны завершаться не более чем за **10 с**;
    * 100 % операций — не более чем за **20 с**.
  * **Автоматическое распределение работ, анализ экспертов и агрегация оценок**:
    * выполнение алгоритма распределения работ между n рецензентами (с приоритетным включением студента-эксперта) для потока до 500 работ должно занимать не более **5 с**;
    * фоновый расчет сходимости оценок студентов с эталонами преподавателя и обновление статуса «студент-эксперт» по итогам проверки — не более **3 с**;
    * проверка условия расхождения Δ ≤ d и расчет итогового балла по одной работе после получения последней рецензии — не дольше **0,5 с**.
  * **Экспорт и синхронизация**:
    * формирование и выгрузка итоговой ведомости курса (до 500 студентов) в форматах CSV / XLSX — не более **5 с**;
    * пакетный импорт и синхронизация списков пользователей из кадровой системы вуза (до 5 000 записей) — не более **30 с**.

- **PR-2 (Приоритет: О) — Пропускная способность и нагрузка (статические и динамические характеристики)**:
  * **Одновременные пользователи**: Система должна поддерживать одновременную активную работу не менее **200 пользователей** в штатном режиме и до **500 одновременных пользователей** в пиковом режиме (период массовой сдачи работ перед дедлайном T_submit) без деградации времени отклика ниже порогов, указанных в PR-1.
  * **Частота транзакций**: Система должна обрабатывать не менее **50 HTTP-запросов в секунду (RPS)** в штатном режиме и не менее **150 RPS** в режиме пиковой нагрузки, включая не менее **20 одновременных потоков загрузки файлов**.
  * **Масштаб хранимых объектов**: Система должна обеспечивать хранение и обработку в рамках одного учебного года не менее **10 000 учётных записей** пользователей, **200 учебных курсов** и **50 000 загруженных работ** (включая рецензии к ним и историю калибровочных проверок).

- **PR-3 (Приоритет: О) — Утилизация аппаратных ресурсов**:
  * **Оперативная память (RAM)**: суммарное потребление оперативной памяти серверными процессами Системы (веб-сервер nginx, сервер приложения, СУБД PostgreSQL) не должно превышать **5 ГБ** в штатном режиме (среднесуточное значение) и **7 ГБ** (не более 85 % от 8 ГБ RAM) в периоды пиковой нагрузки.
  * **Процессорное время (CPU)**: средняя загрузка центрального процессора сервера в штатном режиме не должна превышать **50 %**, а в пиковом режиме — не более **85 %** на интервале в 5 минут.
  * **Дисковое пространство**: при соблюдении квот на загрузку (не более 20 МБ на один файл работы и не более 50 МБ суммарно на одного студента в рамках одного задания) объём основного хранилища файлов и базы данных не должен превышать **200 ГБ** в год, а с учётом хранения резервных копий и системных журналов — не более **500 ГБ**.
  * **Клиентские ресурсы**: веб-интерфейс Системы в браузере пользователя должен потреблять не более **200 МБ** оперативной памяти на одну открытую вкладку.

- **PR-4 (Приоритет: О) — Режим плавной деградации (при перегрузке)**:
  * При превышении пикового порога нагрузки (свыше 500 одновременных пользователей или свыше 20 параллельных загрузок файлов) Система не должна аварийно завершать работу или терять данные: запросы на загрузку файлов и экспорт отчётов должны ставиться в очередь обработки, а фоновые некритичные задачи (импорт расписаний по крону, массовая SMTP-рассылка напоминаний, фоновый перерасчет пула экспертов) должны временно откладываться до снижения нагрузки.

## Ремонтопригодность

- MT-1 (О): Архитектура Системы должна быть строго разделена на три независимых компонента: пользовательский интерфейс (клиентская часть), серверная бизнес-логика и база данных PostgreSQL.
- MT-2 (О): Алгоритм автоматического распределения работ между рецензентами (с учетом обязательного назначения эксперта), алгоритм анализа оценок для выдачи бейджей экспертов, а также алгоритмы проверки разброса оценок по порогу d и отклонения от оценки эксперта должны быть вынесены в отдельные программные модули. Изменение формул расчета, критериев выдачи бейджей или логики распределения не должно требовать переписывания кода других частей Системы.
- MT-3 (О): Все интеграционные интерфейсы — модуль обмена с кадровой системой вуза, модуль авторизации через SSO и модуль отправки почтовых уведомлений — должны быть изолированы от основного ядра системы. При изменении формата данных во внешней кадровой системе вуза изменения должны вноситься только в соответствующий интеграционный модуль.
- MT-4 (О): Система должна поддерживать переключение в режим отладки (включение подробного логирования ошибок) путем изменения параметра в конфигурационном файле, без необходимости остановки сервера или изменения исходного кода Системы.


## Ограничения проекта

Технологические:
   * Только веб-технологии: доступ через браузеры Chrome, Firefox, Edge, Safari; стек — Linux (Debian/Ubuntu LTS), nginx, PostgreSQL 14+.
   * Только открытые протоколы: HTTPS/TLS 1.2+, REST/JSON, SMTP (STARTTLS), LDAP / SAML 2.0 / OpenID Connect.
   * Форматы файлов работ: PDF, DOCX, ODT, ZIP; размер файла до 20 МБ, суммарно на студента по заданию до 50 МБ.

Инфраструктурные:
   * Система входит в ИТ-инфраструктуру вуза и использует её сервисы: кадровая система, SSO, SMTP-сервер.
   * Серверная конфигурация: не менее 4 CPU, 8 ГБ RAM, 500 ГБ диска.
   * Самостоятельная регистрация и локальное хранение паролей не предусмотрены только вход через SSO вуза.
   * Объёмы хранилища: около 200 ГБ, с резервными копиями — до 500 ГБ.

Организационные:
   * Двусторонняя анонимность: статус «студент-эксперт» не раскрывается сокурсникам.
   * Параметры калибровки и экспертной оценки (K_prof, G_exp, δ_exp, d) настраиваются преподавателем для каждого задания без изменения программного кода.
