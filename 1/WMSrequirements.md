# 1. Введение

## 1.1 Цели

Цель документа — зафиксировать требования к WMS, внедрение которой должно повысить количество обработанных единиц товара в единицу времени на складе за счёт:
- **Адресного хранения** — склад разбивается на ячейки; каждая ячейка имеет уникальный машиночитаемый идентификатор.
- **Автоматизированного управления задачами** — система формирует задания для персонала на основе входящих документов.
- **Использования промышленных ТСД** — поддержка Wi-Fi и сканирования штрихкодов при выполнении складских операций.
- **Разделения прихода и расхода** — склад делится на зону хранения и зону отбора, а расход выполняется двухволновым отбором с разделением исполнителей на плейсеров, пакеров и пикеров.

Документ адресован следующим группам:
- **Заказчику** — для проверки соответствия разрабатываемой системы бизнес-потребностям.
- **Команде разработки** — для проектирования архитектуры и реализации функций.
- **Специалистам по тестированию** — для подготовки тестовых сценариев.
- **Эксплуатационному персоналу** — для понимания возможностей и ограничений системы.

## 1.2 Границы применения

Система WMS автоматизирует складские процессы на складах с адресным хранением. В область применения входят:
- **Приход** — обработка приходных накладных, автоматическое определение ячейки размещения в зоне хранения, сканирование товара и ячейки плейсером.
- **Размещение** — адресное хранение, при котором одна ячейка используется для одного SKU; поступивший товар размещается только в зоне хранения.
- **Зоны склада** — деление склада на зону хранения и ограниченную зону отбора; каждая ячейка относится ровно к одной зоне.
- **Расход** — обработка расходных накладных и двухволновой отбор: пополнение зоны отбора пакерами (первая волна), отбор и вынос товара пикерами (вторая волна).
- **Перемещение** — внутреннее перемещение товара между ячейками, в том числе пополнение зоны отбора из зоны хранения.
- **Сборка** — комплектация заказов по расходным документам; выполняется пикерами во второй волне.
- **Отгрузка** — вынос отобранного товара к транспорту или в место дальнейшей передачи.
- **Управление задачами** — автоматическое создание задач для персонала на основе входящих документов и их распределение между грузчиками соответствующей категории.
- **Администрирование** — управление учётными записями, правами доступа, категориями грузчиков, справочниками (ячейки и их зоны, SKU) и настройками системы.

В документ не входят:
- **Бухгалтерский и налоговый учёт** — не является предметом WMS.
- **Автоматизация транспорта и робототехники** — не рассматривается.
- **Внутреннее проектирование базы данных и алгоритмов** — кроме внешне наблюдаемого поведения.
- **Разбор ситуаций несоответствия товаров вне системы** — порядок действий персонала при расхождении данных и фактического товара определяется вне WMS.
- **Выбор конкретных моделей серверного оборудования, СУБД и каналов связи** — в документе конкретные технологии не фиксируются.

## 1.3 Термины и аббревиатуры

|---|---|
| **WMS** | Warehouse Management System — система управления складом |
| **SKU** | Stock Keeping Unit — единица складского учёта, тип товара |
| **ТСД** | Терминал сбора данных, промышленный hand-held с Wi-Fi и сканером штрихкодов |
| **Ячейка** | Место хранения на складе, имеющее уникальный машиночитаемый идентификатор, состоящий из частей «участок, стеллаж, ярус, позиция»; относится ровно к одной зоне — хранения или отбора |
| **Штрихкод** | Машиночитаемый идентификатор ячейки, товара или документа |
| **Цифровой код** | Числовой код, нанесённый рядом со штрихкодом; используется для ручного ввода при отказе сканирования |
| **Приход** | Операция поступления товара на склад |
| **Размещение** | Определение ячейки зоны хранения для поступившего товара |
| **Расход** | Операция выбытия товара со склада по расходной накладной; выполняется двухволновым отбором |
| **Перемещение** | Внутреннее перемещение товара между ячейками |
| **Сборка** | Комплектация заказов по расходным документам; выполняется пикерами во второй волне |
| **Отгрузка** | Вынос отобранного товара к транспорту или в место дальнейшей передачи |
| **Задача** | Автоматически сформированное задание для грузчика |
| **Администратор** | Пользователь, управляющий учётными записями, правами доступа, справочниками и настройками системы |
| **Оператор** | Пользователь, обрабатывающий первичные документы |
| **Грузчик** | Исполнитель физических операций на складе; грузчики делятся на три категории: плейсер, пакер, пикер |
| **Плейсер** | Грузчик, размещающий поступивший товар в ячейках зоны хранения |
| **Пакер** | Грузчик, пополняющий зону отбора: перемещает недостающий товар из зоны хранения в зону отбора (первая волна) |
| **Пикер** | Грузчик, отбирающий товар из зоны отбора и выносящий его к транспорту или в место дальнейшей передачи (вторая волна) |

| **Зона отбора** | Ограниченный набор самых удобных для отгрузки ячеек, например нижние ярусы стеллажей; вторая волна ведётся только из неё |
| **Двухволновой отбор** | Способ выполнения расхода: первая волна — пополнение зоны отбора, вторая — отбор и вынос товара |
| **Пополнение** | Перемещение товара из ячейки зоны хранения в ячейку зоны отбора |

| **Накладная** | Первичный документ на поступление (приходная) или выбытие (расходная) товара; поступает по электронной почте и на бумажном носителе |

| **Свободный остаток** | Остаток SKU за вычетом резерва; считается по всему складу или по одной зоне |
| **Активная задача** | Задача грузчика в статусе «назначена» или «выполняется» |

# 2. Общее описание

## 2.1 Описание изделия

WMS — самостоятельное программное изделие, не входящее в состав более крупной системы. Изделие состоит из серверной части, веб-интерфейсов администратора и оператора и мобильного приложения для ТСД. Внешние связи изделия: почтовый сервис (приём входящих документов), ТСД и рабочие станции пользователей. Интеграция с другими информационными системами заказчика, в том числе с бухгалтерским учётом, не предусмотрена.

### 2.1.1 Интерфейсы системы
- **Источник входящих документов** — электронная почта и бумажная накладная.
- **Электронная почта** — содержит идентификатор документа, наполнение и количество.
- **Бумажная накладная** — содержит штрихкод, совпадающий со штрихкодом электронной версии документа.

### 2.1.2 Интерфейсы пользователя
- **Интерфейс администратора** — панель управления учётными записями, ролями, правами доступа, структурой склада, справочником SKU и настройками системы; работа с накладными не предусмотрена.
- **Интерфейс оператора** — веб-форма для просмотра и обработки входящих документов, фильтрации по статусу; доступ только к первичным документам.
- **Интерфейс грузчика** — приложение на ТСД с крупными кнопками и простым интерфейсом, общее для плейсеров, пакеров и пикеров; грузчик видит только задачи своей категории; ввод данных — сканирование штрихкодов, при необходимости — ручной ввод цифрового кода.

### 2.1.3 Интерфейсы аппаратных средств ЭВМ
- **Промышленные ТСД** — поддержка Wi-Fi и сканирования штрихкодов.
- **Сервер приложений** — размещение WMS и обработка данных.
- **Рабочие станции операторов и администратора** — доступ к веб-интерфейсу.
- **Сетевые точки доступа Wi-Fi** — покрытие склада для работы ТСД.

### 2.1.4 Интерфейсы программного обеспечения
- **Хранилище данных** — хранение данных WMS.
- **Операционная система ТСД** — среда работы мобильного приложения.
- **Веб-браузер** — доступ к интерфейсам администратора и оператора.
- **Почтовый сервис** — приём входящих документов на электронную почту.

### 2.1.5 Интерфейсы коммуникаций
- **Беспроводная сеть Wi-Fi** — основная среда связи с ТСД.
- **Сетевые протоколы** — базовый обмен данными.
- **Защищённые протоколы передачи данных** — защита обмена.

### 2.1.6 Ограничения памяти
- **ТСД** — объём оперативной и постоянной памяти ограничен; минимальные характеристики ТСД фиксируются в соглашении об оборудовании [СОГЛ-ОБ].
- **Мобильное приложение** — рассчитано на работу в условиях ограниченных ресурсов ТСД.
- **Серверная память** — объём определяется при проектировании [TBD-01].

### 2.1.7 Действия
- **Нормальные и специальные действия, необходимые пользователям** — работа в сменах; приход, размещение, расход двухволновым отбором (пополнение зоны отбора и отбор), перемещение, сборка, отгрузка; обработка исключительных ситуаций.
- **Различные способы действий в организации пользователя** — операции, инициируемые оператором (обработка документов) и грузчиками трёх категорий — плейсерами, пакерами и пикерами (сканирование и подтверждение задач).
- **Периоды диалоговых действий и периоды действий, оставленных без отклика** — сеансы работы оператора с веб-интерфейсом и грузчика с ТСД; длительность бездействия до автоматического завершения сеанса — [TBD-02].
- **Функции поддержки обработки данных** — ведение журналов операций и статусов задач; обработка приходных и расходных накладных; состав отчётности — [TBD-03].
- **Действия резервного копирования и восстановления** — система выполняет резервное копирование данных по расписанию и восстанавливает данные из резервной копии (NFR-AVL-04); периодичность копирования и срок хранения копий — [TBD-04].

### 2.1.8 Требования по адаптации к месту эксплуатации
Перед вводом системы в эксплуатацию на конкретном складе выполняются следующие действия по адаптации:
- **Описание структуры склада** — занесение ячеек хранения, их идентификаторов (штрихкодов) и цифровых кодов, отнесение каждой ячейки к зоне хранения или зоне отбора (FR-ADM-04); состав зоны отбора — [TBD-26].
- **Заполнение справочника SKU** — занесение типов товара с их штрихкодами и цифровыми кодами (FR-ADM-05).
- **Создание учётных записей** — заведение пользователей, назначение им ролей, а грузчикам — категорий (FR-ADM-01, FR-ADM-02).
- **Настройка параметров** — указание почтового ящика для приёма документов и прочих параметров (FR-ADM-06).
- **Подключение ТСД** — установка мобильного приложения на ТСД склада и подключение их к сети Wi-Fi склада (IF-SW-02, IF-COM-01).

Все действия по адаптации выполняются средствами системы без изменения её исходного кода.

## 2.2 Функции изделия

На текущем этапе зафиксированы следующие функции WMS:
- **Ведение адресного хранения** — склад разбивается на ячейки; каждая ячейка имеет уникальный машиночитаемый идентификатор; в одной ячейке хранится один SKU; один SKU может храниться в нескольких ячейках; каждая ячейка относится к зоне хранения или зоне отбора.
- **Валидация входящих документов** — проверка приходных и расходных накладных; при выявлении несоответствия документ не передаётся в работу.
- **Автоматическая генерация задач** — задания для грузчиков на основе входящих документов.
- **Управление размещением** — система определяет ячейку зоны хранения для поступившего товара.
- **Управление назначением задач** — система распределяет задачи между грузчиками соответствующей категории.
- **Приход** — система указывает ячейку зоны хранения, плейсер сканирует ячейку и товар, подтверждает размещение.
- **Расход** — выполняется двухволновым отбором: если товара в зоне отбора не хватает, пакеры перемещают недостающее количество из зоны хранения (первая волна); затем пикеры отбирают товар из зоны отбора и выносят его к транспорту или в место дальнейшей передачи (вторая волна).
- **Сборка** — комплектация заказов по расходным документам; выполняется пикерами во второй волне.
- **Отгрузка** — вынос отобранного товара к транспорту или в место дальнейшей передачи.
- **Поддержка ТСД** — получение задач, сканирование штрихкодов, подтверждение операций.
- **Ручной ввод цифрового кода** — при отказе сканирования грузчик вводит числовой код вручную.
- **Управление учётными записями и правами доступа** — роли и полномочия пользователей.
- **Мониторинг статусов задач** — контроль выполнения операций.
- **Обработка ошибок сканирования** — реакция на некорректные штрихкоды и исключительные ситуации.

## 2.3 Характеристики пользователей

На текущем этапе зафиксированы следующие роли:

1. **Администратор**
   - **Зона ответственности** — управление учётными записями, правами доступа, справочником SKU, структурой склада (ячейками), настройками системы.
   - **Интерфейс** — веб-интерфейс.
   - **Требования к подготовке** — знание основ администрирования информационных систем.

2. **Оператор**
   - **Зона ответственности** — обработка входящих документов: просмотр, сопоставление электронной и бумажной накладных, контроль результатов валидации.
   - **Интерфейс** — веб-интерфейс.
   - **Особенности работы** — документы поступают в систему автоматически по электронной почте; система автоматически валидирует документ, а после сопоставления оператором с бумажной накладной создаёт задачи.
   - **Требования к подготовке** — базовое знание складских процессов и уверенное владение ПК.

3. **Грузчик**
   - **Зона ответственности** — физические операции на складе. Грузчики делятся на три категории: плейсеры (приход), пакеры (первая волна расхода — пополнение зоны отбора) и пикеры (вторая волна — отбор и вынос); категорию грузчика задаёт администратор.
   - **Интерфейс** — мобильное приложение на ТСД, общее для всех категорий; грузчик получает только задачи своей категории.
   - **Особенности работы** — при необходимости использует ручной ввод цифрового кода.
   - **Требования к подготовке** — базовые навыки работы с ТСД; глубокие технические знания не требуются.

Категории грузчиков:

| Категория | Когда работает | Где работает | Что делает |
|---|---|---|---|
| Плейсер | Приход | Зона хранения | Размещает поступивший товар: сканирует товар и ячейку зоны хранения, подтверждает размещение |
| Пакер | Расход, первая волна — если товара в зоне отбора не хватает | Из зоны хранения в зону отбора | Перемещает недостающее количество: сканирует исходную ячейку, товар и целевую ячейку, подтверждает перемещение |
| Пикер | Расход, вторая волна — после завершения связанной первой волны | Зона отбора | Отбирает товар и выносит его к транспорту или в место дальнейшей передачи: сканирует товар и ячейку, подтверждает вынос |

## 2.4 Ограничения

На текущем этапе приняты следующие ограничения. Ограничения пронумерованы и используются в разделе 3 как источники CR-nn.

- **CR-01. Один SKU в одной ячейке** — в одной ячейке хранения хранится один тип товара.
- **CR-02. Использование ТСД** — для работы грузчиков применяются промышленные ТСД с поддержкой Wi-Fi и сканирования штрихкодов.
- **CR-03. Один SKU — несколько ячеек** — один SKU может храниться в нескольких ячейках одновременно.
- **CR-04. Наличие цифровых кодов** — рядом со штрихкодами на товарах и ячейках нанесены цифровые коды для ручного ввода.
- **CR-05. Разбор несоответствий вне системы** — ситуации несоответствия товаров разрешаются персоналом вне WMS.
- **CR-06. Отсутствие робототехники** — система не рассматривает автоматические транспортные средства и роботизированные системы.
- **CR-07. Оборудование заказчика и свобода выбора технологий** — система работает на сервере и ТСД, предоставляемых заказчиком; их модели фиксируются в соглашении об оборудовании [СОГЛ-ОБ] и настоящей спецификацией не предписываются. Выбор СУБД и языков программирования остаётся за командой разработки.
- **CR-08. Покрытие Wi-Fi** — склад оснащается точками доступа Wi-Fi с покрытием, достаточным для работы ТСД на всей территории склада; оснащение обеспечивается заказчиком и не входит в разработку WMS.
- **CR-09. Одна ячейка — одна зона** — каждая ячейка склада относится ровно к одной зоне: зоне хранения или зоне отбора.
- **CR-10. Ограниченная зона отбора** — зона отбора ограничена набором самых удобных для отгрузки ячеек (например, нижние ярусы стеллажей); её состав задаётся заранее заказчиком.

## 2.5 Предположения и зависимости

На текущем этапе приняты следующие предположения и зависимости:
- **Стабильная сеть Wi-Fi** — на складе доступна стабильная сеть Wi-Fi.
- **Наличие ТСД** — заказчик предоставляет ТСД в количестве, достаточном для работы смены.
- **Формат входящих документов** — документ поступает на электронную почту (идентификатор, наполнение, количество) и на бумажном носителе; штрихкод на бумажной накладной совпадает со штрихкодом электронной версии.
- **Корректные штрихкоды и цифровые коды** — штрихкоды и цифровые коды на товарах и ячейках корректны и читаемы.
- **Обучение персонала** — персонал обучен работе с WMS и ТСД.
- **Численность исполнителей** — в каждой смене работают грузчики всех трёх категорий в количестве, достаточном для выполнения задач; численность и соотношение категорий — [TBD-16].
- **Серверная инфраструктура** — доступна и соответствует требованиям.
- **Пересмотр требований** — при изменении этих предположений требования могут быть пересмотрены.

# 3. Детальные требования

В данном разделе приводятся детальные требования к системе. Общее описание изделия, функций, пользователей, ограничений и предположений приведено в разделе 2 и здесь не повторяется.

Раздел организован по классам пользователей в соответствии с шаблоном IEEE 830 «Организация раздела 3 по классам пользователей»: 3.1 — внешние интерфейсы, 3.2 — функциональные требования, 3.3 — производительность, 3.4 — ограничения проектирования, 3.5 — атрибуты программной системы, 3.6 — прочие требования. Функциональные требования (3.2) сгруппированы по ролям — администратор, оператор, грузчик, — поскольку у ролей разные интерфейсы, зоны ответственности и сценарии работы. Требования к грузчикам (3.2.3) разделены на общие для всех категорий и требования к каждой категории: плейсеру, пакеру и пикеру. Отдельно вынесены требования к взаимодействию с ТСД (ТСД не разрабатывается, описываются совместимость и характер взаимодействия), системные правила, не привязанные к одной роли, и нефункциональные требования. 
Раздел описывает, что должна делать система, а не бизнес-процесс. Условия, которые обеспечивает заказчик (оснащение склада, маркировка товаров и ячеек), приведены в разделе 2 как ограничения CR и предположения и используются здесь только как источники.
Каждое требование оформлено по единому шаблону, имеет уникальный идентификатор со сквозной нумерацией внутри группы и ссылается на источник — бизнес-требование (BR), пользовательское требование (UR) или ограничение (CR). Требований без источника нет. Сводная трассировка приведена в приложении А.

**Шаблон требования.** Каждое детальное требование оформлено по единому шаблону. Шаблон включает следующие атрибуты:

- **ID** — уникальный идентификатор требования; используется для прямой трассируемости.
- **Заголовок** — краткая формулировка сути требования.
- **Описание** — полная формулировка требования в виде утверждения со словом «должен (должна, должно)», для требований к поведению — «Система должна…»; должно быть корректным, однозначным, полным и проверяемым.
- **Приоритет** — степень необходимости требования: **обязательное**, **условное**, **необязательное**.
- **Источник** — ссылка на бизнес-требование (BR), требование пользователя (UR) или ограничение (CR), из которого выросло данное требование; обязателен для каждого требования; обеспечивает обратную трассируемость.
- **Стабильность** — степень стабильности требования: **высокая**, **средняя**, **низкая**.
- **Ссылки** — идентификаторы связанных требований; обеспечивает прямую трассируемость.
- **Способ проверки** — **осмотр**, **анализ**, **демонстрация**, **тестирование**.
- **Риск** — **высокий**, **средний**, **низкий**.

Неизвестные на момент составления значения обозначаются [TBD-nn]; для каждого из них в приложении Б указаны причина, ответственный и срок определения.

Обозначения источников:
- **BR** — бизнес-требование (подраздел 1.6);
- **UR** — требование пользователя (подраздел 2.7);
- **CR** — ограничение (подраздел 2.4).

## 3.1 Требования к внешним интерфейсам

### 3.1.1 Интерфейсы пользователя

**IF-UI-01. Интерфейс администратора.**
Система должна предоставлять администратору веб-интерфейс, доступный через браузер на рабочей станции, со следующими разделами: управление учётными записями, управление ролями и категориями грузчиков, настройка прав доступа, управление структурой склада (ячейки и их зоны), ведение справочника SKU, настройка параметров системы, просмотр журналов. Работа с накладными в интерфейсе администратора не предусмотрена. Интерфейс состоит из веб-страниц с формами и таблицами; вход — по учётным данным администратора (NFR-SEC-05).
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01.
- Ссылки: IF-HW-03, IF-SW-03, FR-ADM-01…FR-ADM-07, NFR-SEC-05.
- Способ проверки: демонстрация.
- Риск: низкий.

**IF-UI-02. Интерфейс оператора.**

## 3.2 Функциональные требования

Функциональные требования определяют фундаментальные действия, которые должны происходить в системе при получении и обработке входных данных и при формировании выходных данных. Требования сгруппированы по классам пользователей.

### 3.2.1 Класс пользователей «Администратор»

**FR-ADM-01. Управление учётными записями.**
Система должна позволять администратору создавать, просматривать, изменять и удалять учётные записи пользователей. Каждая учётная запись должна содержать идентификатор пользователя, имя, роль, для грузчика — категорию (FR-ADM-02), и статус (активна/заблокирована).
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01.
- Ссылки: IF-UI-01, FR-ADM-02, FR-ADM-03, NFR-LDB-01.
- Способ проверки: демонстрация.
- Риск: низкий.

**FR-ADM-02. Назначение ролей.**
Система должна позволять администратору назначать пользователю одну из ролей: администратор, оператор, грузчик, а грузчику — одну категорию: плейсер, пакер или пикер. Роль определяет доступные пользователю функции и интерфейсы, категория — задачи, которые назначаются грузчику (FR-SYS-02). Изменение категории грузчика, у которого есть активные задачи, не допускается.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01, BR-05, BR-06.
- Ссылки: IF-UI-01, FR-ADM-01, FR-ADM-03, FR-ADM-04, FR-SYS-02.
- Способ проверки: демонстрация.
- Риск: низкий.

**FR-ADM-03. Управление правами доступа.**
Система должна позволять администратору настраивать для каждой роли перечень доступных разделов и операций в пределах функций этой роли (администратор — 3.2.1, оператор — 3.2.2, грузчик — 3.2.3). Пользователь получает права доступа своей роли.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: UR-ADM-01.
- Ссылки: IF-UI-01, FR-ADM-01, FR-ADM-02, FR-OPR-07, NFR-SEC-01.
- Способ проверки: демонстрация.
- Риск: средний.

**FR-ADM-04. Управление структурой склада.**
Система должна позволять администратору создавать, просматривать, изменять и удалять ячейки хранения, задавать их уникальные машиночитаемые идентификаторы (штрихкоды) и цифровые коды, а также относить каждую ячейку ровно к одной зоне: зоне хранения или зоне отбора. Состав зоны отбора — [TBD-26]. Идентификатор ячейки состоит из частей: участок, стеллаж, ярус, позиция. Система не должна допускать удаление ячейки или изменение её зоны, если в ячейке числится товар или она указана в незавершённой задаче.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01, BR-05, CR-01, CR-04, CR-09, CR-10.
- Ссылки: IF-UI-01, FR-ADM-02, FR-SYS-01, FR-SYS-04, NFR-LDB-01.
- Способ проверки: демонстрация.
- Риск: средний.

**FR-ADM-05. Управление справочником товаров.**
Система должна позволять администратору вести справочник SKU: добавлять, просматривать, изменять и удалять записи о типах товара. Каждая запись должна содержать уникальный идентификатор SKU, наименование, штрихкод и цифровой код товара. Штрихкод и цифровой код должны быть уникальны в пределах справочника.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: UR-ADM-01, CR-04.
- Ссылки: IF-UI-01, FR-OPR-04, FR-LDR-03, FR-LDR-04, FR-SYS-03, NFR-LDB-01.
- Способ проверки: демонстрация.
- Риск: средний.

**FR-ADM-06. Настройка параметров системы.**

- Приоритет: условное.
- Стабильность: средняя.

### 3.2.2 Класс пользователей «Оператор»

**FR-OPR-01. Приём документов по электронной почте.**
Система должна принимать входящие документы, поступающие на почтовый ящик, заданный администратором (FR-ADM-06), и извлекать из них идентификатор документа, наполнение (перечень позиций) и количество. Формат письма — [TBD-18]. Если из письма не удаётся извлечь эти данные, система регистрирует документ в статусе «отклонён» с причиной «ошибка формата». Документ с уже зарегистрированным идентификатором повторно не регистрируется; оператору выводится сообщение о повторном поступлении.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01.
- Ссылки: IF-UI-02, IF-SW-04, FR-ADM-06, FR-OPR-02.
- Способ проверки: тестирование.
- Риск: средний.

**FR-OPR-02. Сопоставление электронной и бумажной накладной.**
Система должна обеспечивать сопоставление электронной версии документа с бумажной накладной по штрихкоду, нанесённому на бумажный носитель. Оператор сканирует штрихкод бумажной накладной (или вводит цифровой код) в веб-интерфейсе; система сравнивает его с идентификатором/штрихкодом электронной версии, полученной по электронной почте. При совпадении система отмечает документ как сопоставленный; при отсутствии электронной версии с таким штрихкодом выводит оператору сообщение об ошибке. Документ не передаётся в работу до успешного сопоставления.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-02.
- Ссылки: IF-UI-02, FR-OPR-01, FR-OPR-04, FR-OPR-08.
- Способ проверки: тестирование.
- Риск: средний.

**FR-OPR-03. Просмотр входящих документов.**
Система должна предоставлять оператору веб-форму для просмотра входящих документов и фильтрации по статусу. В карточке документа должны отображаться: идентификатор, наполнение, количество, статус, результат валидации.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01.
- Ссылки: IF-UI-02, FR-OPR-04, FR-OPR-08.
- Способ проверки: демонстрация.
- Риск: низкий.

**FR-OPR-04. Валидация документа.**
Система должна автоматически проверять поступивший документ: каждая позиция должна соответствовать существующему SKU справочника, количество должно быть положительным целым числом; для расходного документа количество каждого SKU не должно превышать его свободный остаток по всему складу — суммарный остаток во всех ячейках за вычетом резерва (FR-SYS-07). Результат валидации (успех или перечень несоответствий по позициям) сохраняется в карточке документа.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01, UR-OPR-02.
- Ссылки: IF-UI-02, FR-ADM-05, FR-OPR-02, FR-OPR-03, FR-OPR-05, FR-OPR-06, FR-SYS-07, NFR-REL-03.
- Способ проверки: тестирование.
- Риск: высокий.

**FR-OPR-05. Отклонение документа при несоответствии.**
При выявлении несоответствия по результатам валидации система не должна передавать документ в работу и должна перевести его в статус «отклонён» с отображением причины оператору. Дальнейший разбор ситуации выполняется персоналом вне системы.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-03, CR-05.
- Ссылки: IF-UI-02, FR-OPR-04, FR-OPR-06, FR-OPR-08, CON-02.
- Способ проверки: тестирование.
- Риск: средний.

**FR-OPR-06. Передача документа в работу.**
При успешной валидации и успешном сопоставлении с бумажной накладной система должна передавать документ в работу (статус «в работе») и формировать задачи для грузчиков: для приходного документа — задачи прихода (FR-SYS-01), для расходного — задачи двухволнового отбора (FR-SYS-08, FR-SYS-09).
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01.
- Ссылки: IF-UI-02, FR-OPR-04, FR-OPR-05, FR-OPR-08, FR-SYS-01, FR-SYS-02, FR-SYS-08, FR-SYS-09.
- Способ проверки: тестирование.
- Риск: высокий.

**FR-OPR-07. Ограничение доступа оператора.**
Интерфейс оператора должен предоставлять доступ только к первичным документам и не позволять изменять структуру склада, справочники или учётные записи.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01.
- Ссылки: IF-UI-02, FR-ADM-03.
- Способ проверки: демонстрация.
- Риск: низкий.

**FR-OPR-08. Статусы документа.**
Система должна вести статус каждого входящего документа: «получен», «сопоставлен», «отклонён», «в работе», «выполнен». Документ переходит в статус «выполнен», когда выполнены все задачи по нему: для приходного документа — задачи прихода, для расходного — задачи второй волны по всем позициям. Оператор должен иметь возможность фильтровать документы по любому из статусов.
- Приоритет: обязательное.
- Стабильность: средняя.

### 3.2.5 Системные правила

Правила, которые выполняются системой автоматически и не относятся к одному классу пользователей.

**FR-SYS-01. Выбор ячейки для размещения.**
При формировании задачи прихода (размещения) система должна выбирать ячейку зоны хранения по следующим правилам:
- Кандидатами являются только ячейки зоны хранения, которые пусты (остаток равен нулю, FR-SYS-07) либо уже содержат тот же SKU. Ограничение по вместимости ячейки — [TBD-19].
- Ячейки, занятые другим SKU, а также ячейки, указанные в незавершённой задаче прихода другого SKU (ожидающие прихода), пропускаются.
- Среди кандидатов выбирается первая по возрастанию уникального машиночитаемого идентификатора.
- Идентификаторы сравниваются последовательно по частям «участок, стеллаж, ярус, позиция» (FR-ADM-04); числовые части сравниваются как числа, буквенные — по алфавиту.
- Если подходящей ячейки нет, система не передаёт документ в работу, переводит его в статус «отклонён» и отображает оператору причину «нет свободной ячейки в зоне хранения».
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-02, BR-05, UR-OPR-01, CR-09.
- Ссылки: FR-ADM-04, FR-OPR-06, FR-LDR-07, FR-SYS-06, FR-SYS-07.
- Способ проверки: тестирование.
- Риск: средний.

**FR-SYS-02. Назначение задачи грузчику.**
При формировании задачи система должна назначать её грузчику соответствующей категории: задачу прихода — плейсеру, задачу пополнения — пакеру, задачу второй волны — пикеру; категория исполнителя прочих задач перемещения — [TBD-17]. Среди грузчиков этой категории с активной учётной записью выбирается грузчик с наименьшим количеством активных задач. Активными для грузчика считаются назначенные ему задачи в статусах «назначена» и «выполняется». При равенстве количества активных задач у нескольких грузчиков задача назначается грузчику с наименьшим идентификатором пользователя. Если грузчиков нужной категории с активной учётной записью нет, задача остаётся в статусе «создана» и назначается по этому же правилу при появлении такого грузчика.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-03, BR-06, UR-OPR-01.
- Ссылки: IF-UI-03, FR-ADM-02, FR-OPR-06, FR-LDR-01.
- Способ проверки: тестирование.
- Риск: средний.

**FR-SYS-05. Мониторинг статусов задач.**

Грузчику отображаются только задачи в статусах «назначена» и «выполняется»; задачи во всех статусах доступны администратору в журнале (FR-ADM-07); оператор видит ход выполнения через статус документа (FR-OPR-08).

**FR-SYS-06. Выбор ячеек при расходе.**
При формировании задач по расходному документу (FR-SYS-08) система должна выбирать ячейки по следующим правилам:
- Ячейки, из которых берётся товар (ячейки зоны отбора для второй волны и ячейки зоны хранения — источники пополнения): кандидатами являются ячейки нужной зоны с требуемым SKU и ненулевым свободным остатком (остаток за вычетом резерва, FR-SYS-07); выбирается первая по возрастанию уникального идентификатора (порядок сравнения — как в FR-SYS-01); если свободного остатка выбранной ячейки недостаточно, используются следующие ячейки в том же порядке до покрытия требуемого количества.
- Целевая ячейка зоны отбора при пополнении выбирается по правилу [TBD-29]; ячейка, указанная целевой в незавершённой задаче пополнения, считается занятой SKU этой задачи.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-02, BR-03, BR-06, CR-03, CR-09.
- Ссылки: FR-LDR-08, FR-LDR-12, FR-SYS-01, FR-SYS-03, FR-SYS-07, FR-SYS-08, FR-SYS-10.
- Способ проверки: тестирование.
- Риск: средний.

**FR-SYS-07. Учёт остатков и резерва.**
Система должна хранить для каждой ячейки её зону, SKU, остаток и резерв. Подтверждение задачи прихода увеличивает остаток ячейки; подтверждение задачи второй волны уменьшает остаток и резерв ячейки зоны отбора; подтверждение перемещения, в том числе пополнения, уменьшает остаток исходной ячейки и увеличивает остаток целевой. Количество, учтённое при формировании задач по позиции расходного документа, резервируется и исключается из свободного остатка до подтверждения соответствующей задачи; при подтверждении пополнения резерв переходит вместе с товаром в целевую ячейку. Резерв не может быть использован для других документов. Ячейка с нулевым остатком считается пустой и не привязана к SKU.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-02, BR-06, CR-01, CR-03.
- Ссылки: FR-OPR-04, FR-LDR-05, FR-LDR-12, FR-SYS-01, FR-SYS-04, FR-SYS-06, FR-SYS-08, FR-SYS-10, NFR-REL-03.
- Способ проверки: тестирование.
- Риск: высокий.

**FR-SYS-08. Двухволновой отбор.**
При передаче расходного документа в работу система должна:
- проверить свободный остаток по всем позициям: если хотя бы по одной позиции свободный остаток SKU по всему складу меньше требуемого количества, документ не передаётся в работу, переводится в статус «отклонён», а оператору отображается причина «недостаточно товара»;
- по каждой позиции, для которой свободный остаток в зоне отбора не меньше требуемого количества, зарезервировать требуемое количество в ячейках зоны отбора (FR-SYS-06); если первая волна по позиции не требуется, сразу сформировать задачи второй волны;
- по каждой позиции, для которой свободный остаток в зоне отбора меньше требуемого количества, зарезервировать имеющийся свободный остаток зоны отбора и недостающее количество в ячейках зоны хранения (FR-SYS-06), а на недостающее количество сформировать задачи первой волны (пополнения). Пополнение по расходному документу выполняется на недостающее количество; возможность пополнения до максимального остатка определяется по [TBD-28];
- если для позиции сформированы задачи первой волны, задачи второй волны по этой позиции не формировать до выполнения всех задач первой волны (FR-SYS-09). После их выполнения сформировать задачи второй волны по каждой ячейке зоны отбора, в которой для позиции зарезервирован товар.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-06, UR-LDR-05, UR-LDR-06, CR-10.
- Ссылки: FR-OPR-06, FR-LDR-08, FR-LDR-12, FR-SYS-06, FR-SYS-07, FR-SYS-09, FR-SYS-10.
- Способ проверки: тестирование.
- Риск: высокий.

**FR-SYS-09. Очерёдность волн.**
Система не должна формировать задачи второй волны по позиции расходного документа, пока не выполнены все задачи первой волны по этой позиции. После подтверждения последней задачи первой волны система формирует задачи второй волны по этой позиции с учётом резерва в ячейках зоны отбора (FR-SYS-08). Если первая волна по позиции не требуется, задачи второй волны формируются сразу. Резервирование товара для второй волны само по себе не означает немедленного формирования задач второй волны.
- Приоритет: обязательное.
- Стабильность: высокая.

## 3.6 Прочие требования

### 3.6.1 Логические требования к базе данных

**NFR-LDB-01. Состав данных.**
Система должна обеспечивать хранение следующих логических сущностей и связей между ними:
- пользователь — имеет одну роль, грузчик — также одну категорию (плейсер, пакер, пикер);
- роль — определяет набор прав доступа;
- ячейка хранения — относится к одной зоне (хранения или отбора), содержит не более одного SKU, его остаток и резерв;
- SKU — может находиться в нескольких ячейках;
- входящий документ — содержит одну или несколько позиций (SKU и количество) и имеет статус;
- задача — относится к одному документу (для расходного — к позиции документа и волне), одному SKU, одной или двум ячейкам (для перемещения и пополнения), содержит количество и назначена одному грузчику соответствующей категории;
- журнал — записи об операциях, статусах задач и событиях безопасности.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: BR-02, BR-03, BR-05, BR-06.
- Ссылки: IF-SW-01, FR-ADM-01, FR-ADM-04, FR-ADM-05, FR-SYS-05, CMP-03, NFR-AVL-04, NFR-LDB-03.
- Способ проверки: анализ.
- Риск: средний.

**NFR-LDB-02. Целостность данных.**
Система должна обеспечивать следующие ограничения целостности данных: уникальность идентификаторов, штрихкодов и цифровых кодов ячеек и SKU; не более одного SKU в ячейке; принадлежность каждой ячейки ровно одной зоне; неотрицательность остатков; резерв ячейки не превышает её остаток; невозможность удаления ячейки, SKU или пользователя, на которых ссылаются незавершённые задачи.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: CR-01, CR-09.
- Ссылки: FR-SYS-04.
- Способ проверки: тестирование.
- Риск: высокий.

**NFR-LDB-03. Срок хранения данных.**
Система должна хранить входящие документы, задачи и записи журналов не менее [TBD-24] с момента их создания и обеспечивать их просмотр в течение этого срока.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: UR-ADM-02, UR-OPR-01.
- Ссылки: FR-ADM-07, NFR-SEC-04, NFR-MAINT-02, NFR-LDB-01.
- Способ проверки: анализ.
- Риск: низкий.

### 3.6.2 Требования к пользовательской документации

**DOC-01. Руководство администратора.**
Должно быть разработано руководство администратора, описывающее управление учётными записями, ролями, правами доступа, структурой склада и справочником SKU.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01.
- Ссылки: FR-ADM-01…FR-ADM-05.
- Способ проверки: осмотр.
- Риск: низкий.

**DOC-02. Руководство оператора.**
Должно быть разработано руководство оператора, описывающее работу с входящими документами и их валидацию.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-OPR-01.
- Ссылки: FR-OPR-01…FR-OPR-08.
- Способ проверки: осмотр.
- Риск: низкий.

**DOC-03. Руководство грузчика.**
Должна быть разработана инструкция для грузчика по работе с ТСД и выполнению задач с отдельными разделами для плейсера, пакера и пикера.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-LDR-01.
- Ссылки: FR-LDR-01…FR-LDR-09, FR-LDR-11, FR-LDR-12.
- Способ проверки: осмотр.
- Риск: низкий.

**DOC-04. Язык документации.**
Документация должна быть на русском языке.
- Приоритет: обязательное.
- Стабильность: высокая.
- Источник: UR-ADM-01, UR-OPR-01, UR-LDR-01.
- Ссылки: —.
- Способ проверки: осмотр.
- Риск: низкий.

### 3.6.3 Требования лицензирования

**LIC-01. Лицензии на компоненты.**
Все сторонние компоненты, входящие в систему, должны иметь лицензии, допускающие их коммерческую эксплуатацию заказчиком без ограничения числа пользователей. Перечень сторонних компонентов и их лицензий передаётся заказчику вместе с системой.
- Приоритет: обязательное.
- Стабильность: средняя.
- Источник: CR-07.
- Ссылки: CMP-01…CMP-03.
- Способ проверки: осмотр.
- Риск: низкий.
